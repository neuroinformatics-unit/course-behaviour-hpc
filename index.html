Hardware overview

  • CPU (Central Processing Unit)
    • General-purpose
    • Split into cores (typically between 4 and 64)
    • Each core can run a separate process
    • Typically higher clock speed than GPU (~3-5GHz)
  • GPU (Graphics Processing Unit)
    • Originally for rendering graphics
    • Thousands of cores
    • Optimised for parallel processing of matrix multiplication
    • Typically lower clock speed than CPU (~1-2GHz)

Hardware overview

Primary storage:

  • Cache
    • Small, fast memory
    • Stores frequently accessed data
    • Sits directly on the CPU/GPU
    • Typically in the MB range with multiple levels
  • Main memory (RAM/VRAM)
    • Fast storage for data
    • CPU/GPU can access data quickly
    • Lost when machine is powered off
    • Typically 8-512 GB range

Hardware overview

Secondary storage:

  • Drive storage (HDD/SSD)
    • Much slower than RAM
    • SSDs faster than HDDs
    • Typically in the GB-TB range
  • Network storage (e.g. ceph)
    • Shared storage accessible from multiple machines
    • Typically in the TB-PB range
    • High latency compared to local storage

Performance considerations

  • CPU
    • Frequency is important for single-threaded tasks
    • More cores can be better for parallel tasks
    • Sometimes your local machine is faster than the HPC for CPU tasks
  • GPU
    • Great for parallel tasks (e.g. machine learning)
    • Memory is important - make sure your data fits in VRAM
    • Generation can be important, a new generation is typically ~10 – 20% faster
  • Storage
    • Best if you can keep data in primary memory (Cache/RAM)
    • If data doesn’t fit in memory make sure it’s on fast storage (local)

Introduction to High Performance Computing (HPC)

  • Lots of meanings
  • Often just a system with many machines (nodes) linked together with some/all of:
    • Lots of CPU cores per node
    • Powerful GPUs
    • Lots of memory per node
    • Fast networking to link nodes
    • Fast data storage
    • Standardised software installation

Why?

  • Run jobs too large for desktop workstations
  • Run many jobs at once
  • Efficiency (cheaper to have central machines running 24/7)
  • In neuroscience, typically used for:
    • Analysing large data (e.g. high memory requirements)
    • Parallelising analysis/modelling (run on many machines at once)

pwd and cd: Navigate Directories

  • cd [directory] – Changes the current working directory to the specified directory.
  • cd .. – Move up one directory level.
  • cd /path/to/directory – Go to a specific path.
  • cd ~ or cd – Go to the home directory.
  • cd / – Go to the root directory.
  • pwd – Prints the current working directory.

ls: List Directory Contents

  • ls – Lists files and directories in the current working directory.
  • ls -l – Displays detailed information about each file (permissions, owner, size, etc.).
  • ls -a – Shows all files, including hidden files (files starting with a dot).
  • ls -h – Displays sizes in human-readable format (e.g., KB, MB).
  • ls -lah – Combines the above options.

mkdir: Make Directory

  • mkdir [directory_name] – Creates a new directory with the specified name.
  • mkdir -p /path/to/dir to create nested directories.

rmdir and rm: Remove Directories and Files

  • rm [file]– Removes a file.
  • rmdir [directory] – Removes an empty directory.
  • rm -r [directory] - Removes a directory and its contents recursively.
  • rm -f [file] - Removes to force remove a file (no undo be careful!).

mv and cp: Move, Rename and Copy

  • cp [source] [destination] – Copies a file or directory to the destination.
  • mv [source] [destination] – Moves a file or directory to the destination.
  • mv can also be used to rename a file or directory if the source and destination directories match.
cp file.txt /new/location/
mv file.txt /new/location/
mv old_name.txt new_name.txt

Input and Output

  • echo [text] – Displays text or outputs text to a file.
  • echo $ENV_VAR – Displays the value of an environment variable.
  • touch [filename] – Creates an empty file or updates the timestamp of an existing file.
  • > – Redirects output to a file.
  • >> – Appends output to a file.
echo "Hello, Linux!"
touch file.txt
echo "Hello, Linux!" > file.txt
echo $HOME >> file.txt

View File Contents

  • cat [file] – Displays the contents of a file.
  • less [file] – Opens a file in a scrollable viewer, allowing navigation
  • nano [file] – Opens a file in the nano text editor for editing

Permissions and Ownership

  • chmod [permissions] [file] – Changes the permissions of a file or directory
  • Numeric notation is based on binary representation of permissions:
    • Read: 100 (4)
    • Write: 010 (2)
    • Execute: 001 (1)
    • chmod 755 file.txt sets permissions to rwxr-xr-x (user has read, write, execute; group and others have read and execute)
  • Symbolic notation uses letters:
    • r for read, w for write, and x for execute
    • u for user, g for group, and o for others (if skipped it applies to all)
    • chmod u+x file.txt adds execute permission for the user
    • chmod go-w file.txt removes write permission for group and others

watch: Monitor Command Output

  • watch [command] – Repeatedly runs a command at intervals and displays the result.
  • Use watch -n [seconds] [command] to change the interval.
watch -n 0.5 nvidia-smi

man and help: Get Help

  • man [command] – Opens the manual page for a command.
  • help [command] – Provides a short description of built-in commands.
man ls
help cd

|: Pipes!

Description:

  • | – Pipes the output of one command as input to another.
  • Useful for chaining commands together to perform complex operations.
ls | grep ".txt"
cat large_log_file.log | grep "ERROR" | less

Partitions

Think of them as logical queues. Three types:

  • General partitions accessible to all, e.g. cpu, gpu, a100
  • Owned partitions for specific groups, e.g. gpu_saxe, gpu_branco
  • Backfilling partitions to utilize spare hardware, e.g. cpu_backfill, gpu_lowp

Submitting SLURM jobs

Types of jobs

  • Interactive jobs: run commands with real-time feedback (e.g. for debugging)
  • Batch jobs: submit scripts to run in the background
    • Array batch jobs: submit multiple similar jobs at once

Warning

To spare the gateway node, always start a job (interactive or batch) before doing anything beyond simple filesystem navigation or terminal-based script editing.

Interactive job

Start an interactive job (bash -i) in the cpu partition (-p cpu) in pseudoterminal mode (--pty) with one CPU core (-n 1).

srun -p cpu -n 1 --pty bash -i

Tip

If the cpu partition is busy, you can cancel the request with Ctrl+C and try -p cpu_backfill instead.

Green computing: make every job count

HPC jobs use energy (and emit carbon) whether or not they produce anything useful.

  • Know what each job adds to your research project before running it
  • Test input files and job scripts with small/short jobs (e.g. one video, a few epochs) before scaling up
  • Fail early: make scripts stop at the first error (e.g. set -e in bash batch scripts)
  • Achieve the same goals with fewer jobs, e.g. sample parameter spaces wisely rather than exhaustively

Green computing: request only what you need

  • Request only the CPUs, memory and time your job needs
  • Only request a GPU if your code uses it
  • Cancel jobs that are stuck or misconfigured (scancel <JOBID>)
  • Not urgent? Let CATS (Climate-Aware Task Scheduler) pick the lowest-carbon start time and submit with sbatch --begin

See also SWC/GCNU Scientific Computing wiki

HPC Best Practices

Green computing: check, then right-size

After a job finishes, compare what it used with what you requested:

sacct -j <JOBID> --format=JobID,JobName,State,Elapsed,Timelimit,ReqMem,MaxRSS,AllocCPUS
  • MaxRSS much lower than ReqMem? Request less memory next time
  • Elapsed much shorter than Timelimit? Request less time
  • Estimate your job’s carbon footprint with the Green Algorithms calculator

#!/bin/bash

#SBATCH -J slp_infer # job name
#SBATCH -p gpu # partition
#SBATCH -N 1   # number of nodes
#SBATCH --mem 32G # memory pool for all cores
#SBATCH -n 8 # number of cores
#SBATCH -t 0-01:00 # time (D-HH:MM)
#SBATCH --gres gpu:1 # request 1 GPU
#SBATCH -o slurm.%x.%N.%j.out # write STDOUT
#SBATCH -e slurm.%x.%N.%j.err # write STDERR
#SBATCH --mail-type=ALL
#SBATCH --mail-user=user@domain.com

# Exit immediately if any command fails
set -e

# print GPU info
nvidia-smi

# Load the SLEAP module
module load SLEAP

# Define directories for exported SLEAP job package and videos
SLP_JOB_NAME=mouse044_task1_annotator1.training_job
SLP_JOB_DIR=/ceph/scratch/$USER/$SLP_JOB_NAME
VIDEO_DIR=/ceph/scratch/neuroinformatics-dropoff/SLEAP_HPC_test_data/CalMS21
VIDEO_PREFIX=mouse044_task1_annotator1

# Go to the job directory
cd $SLP_JOB_DIR

# Make a directory to store the predictions
mkdir -p predictions

# Run the inference command
sleap-track $VIDEO_DIR/${VIDEO_PREFIX}.mp4 \
    -m $SLP_JOB_DIR/models/250806_174722.centroid.n=679/training_config.json \
    -m $SLP_JOB_DIR/models/250807_162146.multi_class_topdown.n=679/training_config.json \
    -o predictions/${VIDEO_PREFIX}_predictions.slp \
    --gpu auto \
    --no-empty-frames \
    --batch_size 1

Python on the HPC

Until now, we have used preinstalled modules.

But more realistically, you’ll want to run your own code. In Neuroscience the most popular language is Python.

Goal: run a Python script on the HPC.

Python is an ecosystem

  • There are 800,000+ Python packages, e.g. numpy, pandas, scikit-learn.
  • An environment is a collection of compatible packages.
  • For each “big” piece of analysis you do (spike sorting, pose estimation, downstream analysis) you should have a different environment.
  • Ideally, you want to be able to use the same environment locally or on the HPC.
  • To achieve this, we’ll use uv (alternative to conda, poetry, mamba, …).

Getting started locally (optional)

Let’s create a Python project locally:

  1. Install uv: https://docs.astral.sh/uv/getting-started/installation/

  2. Create a directory called spike_times_analysis

  3. Open the directory in the terminal and check you’re in the right place

pwd
  1. Initialize a Python project using uv
uv init
  1. Add a package
uv add numpy

Files that manage your environment

uv has created a bunch of files. pyproject.toml is a description of your project, including which packages you’ve included. The most important list is the dependencies.

[project]
name = "spike-times-analysis"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.13"
dependencies = [
    "numpy>=2.5.3",
]
  • Task: Add another package using uv add ?? and check your pyproject.toml.

If you give this pyproject.toml file to a friend, they’ll be able to (approximately) remake your environment.

Run some code

Let’s write some code. I’ll save it at spike_times_analysis/scripts/analyse_spikes.py

import numpy as np

# Make fake spike times in seconds
spike_times = np.sort(np.random.uniform(low=0.0, high=10.0, size=200))

inter_spike_intervals = np.diff(spike_times)
mean_isi = np.mean(inter_spike_intervals)
print(mean_isi)

And try to run it

uv run scripts/analyse_spikes.py

What is uv run

uv run ?? does the following sequence of events:

  1. Checks your pyproject.toml and figures out which packages and package versions you need
  2. Creates (or updates) a virtual environment at .venv
  3. Activates the environment
  4. Runs python ??

Where to keep your environment

  • By default, uv saves your environment in your project folder.

  • It also keeps a cache so that if you use the same package in several projects, it can “share” it.

This is usually fine.

  • But on the HPC there are many physical drives “stuck together” to look like the ceph. It’s a good idea to insist that uv uses a cache and environment location on the same physical storage.

  • We can do this by setting the UV_PROJECT_ENVIRONMENT variable, as we’ll see.

Run using a script

The real power of the HPC comes when we can submit jobs to run scripts. Let’s create a bash script called test.sh containing

#!/bin/bash

#SBATCH -p cpu
#SBATCH -N 1
#SBATCH --mem 1G
#SBATCH -n 1 
#SBATCH -t 0-0:1 
#SBATCH -o test_output.out
#SBATCH -e test_error.err

set -e

module load uv
export UV_PROJECT_ENVIRONMENT="/ceph/python_envs/YOURUSERNAME/spike_sort_pipeline"
cd /ceph/scratch/YOURUSERNAME/spike_sort_pipeline/

uv run test.py

and submit it

sbatch test.sh

Real world example

We’re going to use a GPU to spike sort a Neuropixels recording using SpikeInterface and Kilosort.

First, let’s add both these packages to the spike_sort_pipeline project

uv add 'spikeinterface[full]' kilosort

and check they are there

uv pip list

Write a spike sorting pipeline

Make a spike sorting file at spike_sort_pipeline/spike_sort.py

import spikeinterface.full as si
recording = si.read_openephys('/ceph/scratch/neuroinformatics-dropoff/neuropixel2_data')
recording_one_shank = recording.split_by('group')[0]
sorting = si.run_sorter('kilosort4', recording_one_shank, remove_existing_folder=True, use_binary_file=False, verbose=True)

analyzer = si.create_sorting_analyzer(
  sorting=sorting,
  recording=si.bandpass_filter(si.common_reference(recording_one_shank)),
  folder = 'kilosort4_sorting_analyzer',
  format='binary_folder'
)

analyzer.compute(['random_spikes', 'templates', 'unit_locations', 'correlograms', 'spike_amplitudes', 'spike_locations', 'quality_metrics'])

(You can find this file at /ceph/scratch/neuroinformatics-dropoff/spike_sort.py)

And run it (just to test)

uv run spike_sort.py

Submit a proper job

Make a bash script called spike_sort.sh:

#!/bin/bash

#SBATCH -J spike_sort
#SBATCH -p gpu
#SBATCH --gres=gpu:1
#SBATCH -N 1
#SBATCH --mem 32G
#SBATCH -n 8
#SBATCH -t 0-1:0 
#SBATCH -o spike_sort_%j.out
#SBATCH -e spike_sort_%j.err

set -e

module load uv
export UV_PROJECT_ENVIRONMENT="/ceph/python_envs/YOURUSERNAME/spike_sort_pipeline"

cd /ceph/scratch/YOURUSERNAME/spike_sort_pipeline/
uv run spike_sort.py

and submit it

sbatch spike_sort.sh

The output

This script creates a SortingAnalyzer. This is the “end point” of a SpikeInterface spike sorting pipeline. You can take a look at the results using SpikeInterface-GUI.
